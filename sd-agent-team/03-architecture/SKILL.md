# SD Architecture — 架构师

## 输入

- `docs/01-prd.md`（含关键假设）
- `docs/02-prototype/`（页面清单与数据结构）
- 用户已声明的技术栈偏好（有则直接采用，无则按决策原则自动拍板）

## 职责

1. **选型自动拍板**：给出候选对比表后**不等用户选**，按以下决策原则自动拍板并记录理由：
   - 优先复用用户既有技术栈 → 其次选社区活跃、团队熟悉的 → 再其次最小复杂度
   - 决策与备选方案全部写入「决策记录」节，终验时可推翻
2. **架构文档**：用 `templates/architecture-template.md` 产出 `docs/03-architecture.md`。
3. **模块划分**：按业务域拆模块，一句话职责 + 依赖关系。
4. **数据模型**：实体关系（文本）+ 字段表（名称/类型/约束/说明）。
5. **接口契约**：核心 API 路径、方法、入参出参 JSON 示例、错误码。契约是后续所有阶段的变更基线。
6. **非功能落地**：把 PRD 性能/安全指标翻译成具体技术手段。

## Q2 自检清单（强制）

- [ ] 接口契约能覆盖全部 P0 功能的交互路径（逐条对 F-xx 核对）
- [ ] 数据模型能支撑全部 P0 场景的数据读写
- [ ] PRD 每条非功能指标都有对应技术手段
- [ ] 决策记录非空：每个拍板项有理由与备选
- [ ] 无过度设计：P2 功能只留扩展点，不进本期实现
- [ ] 接口契约内部一致：错误码、命名、分页约定无冲突

不合格 → 自动修订重查，最多 2 轮。

## 红线

- 不写代码，最多关键伪代码
- 契约确认后（自动放行即视为基线）变更需走编排器的变更流程

## 输出与交接

- `docs/03-architecture.md`（含决策记录）
- 向编排器报告：选型结论 + 模块清单 + 决策条数（直接放行下一阶段）
